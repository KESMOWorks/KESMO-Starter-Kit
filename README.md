# KESMO Starter Kit

**Version 1.1.0**

The reusable website foundation for KESMO web tools.

> Precision made simple.

## Overview

The KESMO Starter Kit provides the shared structure, design system, branding, accessibility features, search metadata, supporting pages, reusable components, and documentation used by future KESMO projects.

Every new KESMO tool begins with this repository instead of being built from scratch.

The KESMO Pricing Calculator was the first completed KESMO product and served as the original design and quality benchmark. The Starter Kit is now the single source of truth for shared KESMO code, branding, architecture, and improvements.

## Current Status

The Starter Kit is ready to serve as the foundation for future KESMO tools.

Version 1.1.0 introduces a standardized shared page architecture built around reusable Header, Hero, and Footer components.

The current shared components are:

* Header
* Hero
* Footer

These components are generated by `components.js` and used across the standard KESMO pages:

* Home
* About
* Privacy
* 404

The Starter Kit remains a development foundation rather than a public-facing KESMO tool.

The repository is configured as a GitHub Template Repository, allowing every new KESMO project to begin from the same shared foundation while starting with a clean Git history.

## Shared Architecture

Shared page components are managed by `components.js`.

The standard page structure is:

```text
Page
├── Shared Header
├── Shared Hero
├── Page-specific content
└── Shared Footer
```

Each page includes component placeholders:

```html
<div id="site-header"></div>

<main id="main-content">
  <div
    id="page-hero"
    data-eyebrow="..."
    data-title="..."
    data-description="..."
  ></div>

  <!-- Page-specific content -->
</main>

<div id="site-footer"></div>
```

The Hero component supports the following data attributes:

* `data-eyebrow`
* `data-title`
* `data-description`
* `data-note`

Page-specific text remains in the HTML while shared structure and markup remain centralized in `components.js`.

## Shared Development Workflow

The Starter Kit is the single source of truth for shared KESMO improvements.

When an improvement benefits more than one KESMO tool, follow this workflow:

1. Improve the Starter Kit.
2. Verify the improvement in the Starter Kit.
3. Apply the improvement to existing KESMO tools.
4. Use the updated Starter Kit as the foundation for future tools.

If an improvement is first proven inside an existing KESMO tool, copy it back into the Starter Kit before treating it as a shared standard.

### Local Development

KESMO development is performed locally in Visual Studio Code.

The local repository is the active development workspace. The GitHub repository remains the source of truth for the latest published version, and this README is the development source of truth for the project.

Do not assume that a local change is published until it has been committed, pushed to GitHub, and the GitHub Pages deployment has been verified.

For normal development:

1. Clone the repository from GitHub, or pull the latest changes if it has already been cloned.
2. Open the local repository in Visual Studio Code.
3. Make changes locally.
4. Preview the site with the Microsoft Live Preview extension for Visual Studio Code.
5. Test the complete change locally before publishing.
6. Run `git status` and review the modified files.
7. Stage the completed changes with `git add .`.
8. Commit the completed work with a clear message using `git commit -m "Relevant update"`.
9. Push the commit with `git push origin main`.
10. Run `git status` again and confirm that the working tree is clean.
11. Verify the GitHub Pages deployment when it becomes available.
12. Update the README, CHANGELOG, version, release, or tag when appropriate.

The standard Git publishing sequence is:

```bash
git status
git add .
git commit -m "Relevant update"
git push origin main
git status
```

KESMO projects use plain HTML, CSS, and JavaScript. Normal local preview does not require npm, Python, a package manager, a framework, or a build process.

Avoid adding development dependencies solely to preview a static KESMO site when Visual Studio Code Live Preview provides the required local testing environment.

### Source of Truth

Use the following distinction during development:

* **Local repository:** active development workspace.
* **GitHub `main` branch:** latest published source of truth after changes have been pushed.
* **README.md:** development source of truth for architecture, standards, workflow, goals, and project status.
* **GitHub Pages:** public deployed version.

Repository contents and the current README take precedence over previous notes or chat history.

If local files and GitHub differ because work has not yet been pushed, treat the local files as unfinished development work rather than as the published version.

## Accessibility Standards

Every KESMO project should include:

* A working skip link
* A unique page heading
* Semantic page landmarks
* Keyboard-accessible navigation
* Visible focus styles
* Accessible link and button labels
* Meaningful heading order
* Reduced-motion support
* High-contrast support where practical
* Responsive layouts without horizontal overflow

Shared components should not create duplicate headings, skip links, or landmarks.

## Search and Social Standards

Every public KESMO page should include:

* A descriptive page title
* A useful meta description
* A canonical URL
* Open Graph metadata
* X/Twitter Card metadata
* Structured data where appropriate
* A favicon
* A social sharing image
* Accurate `robots.txt`
* Accurate `sitemap.xml`

The custom `404.html` page should not be included in the sitemap.

## SEO Configuration Standard

The search and social metadata in each HTML file should remain together in one clearly marked configuration section inside the `<head>`.

For each page, the following values must describe the same page and project:

* Page title
* Meta description
* Canonical URL
* Open Graph title
* Open Graph description
* Open Graph URL
* Open Graph image
* Open Graph image alternative text
* X/Twitter title
* X/Twitter description
* X/Twitter image
* X/Twitter image alternative text
* Structured-data name
* Structured-data description
* Structured-data URL
* Structured-data image or logo URLs, when included

Do not generate essential search or social metadata with JavaScript. Keep it directly in the HTML so search engines, link-preview services, and other crawlers can read it from the original document.

Do not add a meta keywords tag. Modern Google Search does not use the keywords meta tag for web ranking.

Before publishing, verify that no Starter Kit URL, project name, description, image path, or placeholder remains in any public page.

## Required Before Publishing

Before releasing a KESMO tool built from this Starter Kit:

* Change `robots.txt` to allow search indexing.
* Update `sitemap.xml` with the new tool's URLs.
* Replace all KESMO-Starter-Kit URLs with the new repository URL.
* Update the `<base>` tag in `404.html`.
* Replace the homepage content with the tool interface.
* Review the Privacy Policy for tool-specific features.
* Verify the custom 404 page.
* Test GitHub Pages deployment for the new project.
* Confirm the All KESMO Tools destination is live.
* Confirm there are no broken shared navigation links.

## Maintaining the KESMO Home Site

The central KESMO website:

```text
https://kesmoworks.github.io/
```

serves as the public directory for all published KESMO tools.

The homepage is intentionally simple and should remain focused on helping visitors discover available tools.

When publishing a new KESMO tool:

1. Publish the new tool.
2. Verify the tool is working correctly.
3. Add a new tool card to the KESMO Home page.
4. Link the card to the published tool.
5. Write a short, evergreen description.
6. Verify the new card appears correctly on desktop and mobile.

Tool cards are added manually rather than generated automatically.

This approach:

* Keeps the website fast.
* Requires no build process or external API.
* Works without JavaScript.
* Gives complete control over tool order, names, and descriptions.
* Keeps the homepage stable and easy to maintain as the KESMO collection grows.

## Copying the Starter Kit

Follow this checklist every time you create a new KESMO tool.

### 1. Create the Repository

Create a new public GitHub repository.

Copy the entire KESMO Starter Kit into the new repository.

Enable GitHub Pages.

### 2. Update components.js

Update the `KESMO_CONFIG` object.

Review:

* `repositoryName`
* `projectName`
* `version`
* `toolHomeUrl`
* `kesmoHomeUrl`
* `supportEmail`
* `logoPath`

`toolHomeUrl` normally remains:

```text
index.html
```

`kesmoHomeUrl` should point to the central KESMO website:

```text
https://kesmoworks.github.io/
```

The KESMO logo in the shared Header and Footer should link to `kesmoHomeUrl`.

The All KESMO Tools link should also point to `kesmoHomeUrl`.

The shared Footer should include the official KESMO YouTube link:

```text
https://www.youtube.com/@KESMOWorks
```

### 3. Update Navigation Labels

Update project-specific navigation text where needed.

For example:

```text
Home
```

may become:

```text
Pricing Calculator
```

The About, Privacy, All KESMO Tools, and YouTube links should remain consistent across public KESMO projects unless a project requires different navigation.

### 4. Update Shared Hero Content

Each standard page should use the shared Hero placeholder.

Review:

* `data-eyebrow`
* `data-title`
* `data-description`
* `data-note`, when applicable

Confirm that old hard-coded Hero markup has been removed.

### 5. Update Search and Social Configuration

Every public page contains a clearly marked search and social configuration section inside its `<head>`.

Update every applicable value in that section:

* Page title
* Meta description
* Canonical URL
* Open Graph title
* Open Graph description
* Open Graph URL
* Open Graph image
* Open Graph image alternative text
* X/Twitter title
* X/Twitter description
* X/Twitter image
* X/Twitter image alternative text
* Structured-data name
* Structured-data description
* Structured-data URL
* Structured-data image and logo URLs, when included

Confirm that repeated values match. The canonical URL, Open Graph URL, and structured-data URL should identify the same published page.

### Google Search Console Verification

Tools published beneath:

```text
https://kesmoworks.github.io/
```

are normally covered by the verified root URL-prefix property.

Leave the optional `google-site-verification` meta tag commented out unless Google provides a separate token for the new project or property.

When Google supplies a verification token:

* Use the token exactly as provided.
* Place the verification meta tag inside the homepage `<head>`.
* Do not rename or alter a downloaded Google HTML verification file.
* Do not copy a verification token from an unrelated website or property.
* Do not remove an active verification method after ownership has been confirmed, because Google may check it again later.

Pages to review:

* `index.html`
* `about.html`
* `privacy.html`
* `404.html`, when it contains public metadata

### 6. Replace Starter Kit Content

* Replace the homepage with the new tool.
* Update the About page for the new tool.
* Review the Privacy Policy for the tool's actual behavior.
* Update the social sharing image if appropriate.
* Remove Starter Kit-specific instructions from public-facing content.

### 7. Update Search Files

#### robots.txt

Before publishing a public KESMO tool, change:

```text
Disallow: /
```

to:

```text
Allow: /
```

#### sitemap.xml

* Replace every Starter Kit URL with the new repository URL.
* Verify that `404.html` is not included.
* Verify that every listed page is publicly available.

### 8. Update 404.html

* Update the `<base>` path to the new repository.
* Confirm it loads `components.js`.
* Confirm it uses the shared Header.
* Confirm it uses the shared Hero.
* Confirm it uses the shared Footer.
* Confirm all recovery links work.

Example:

```html
<base href="https://kesmoworks.github.io/NEW-REPOSITORY/">
```

### 9. Test Everything

Verify:

* Home page
* About page
* Privacy page
* Custom 404 page
* Shared Header
* Shared Hero
* Shared Footer
* KESMO Header logo → KESMO Home
* KESMO Footer logo → KESMO Home
* Mobile layout
* Desktop layout
* Keyboard navigation
* Skip link
* Footer links
* Email link
* All KESMO Tools link
* YouTube link and icon
* Social sharing image
* Favicon

### 10. Final Review

Confirm:

* No unintended Starter Kit text remains.
* No placeholder content remains.
* No duplicate skip links remain.
* No hard-coded shared components remain.
* No broken links remain.
* No console errors appear.
* Accessibility still works.
* Search metadata is accurate.
* The tool feels production-ready.
* The README accurately reflects the repository.

Only after every applicable item above is complete should the new KESMO tool be considered ready for publication.

## Livestream Documentation

KESMO development may be documented publicly through YouTube livestreams.

The stream should focus on authentic development, testing, problem solving, and progress rather than requiring constant audience interaction.

Before each livestream, define one clear and achievable development goal.

Whenever practical, structure each stream like this:

1. Starting Soon
2. Brief welcome
3. State today's concrete goal
4. Show the current version
5. Build and test locally
6. Review the completed change
7. Commit and push when ready
8. Verify the deployment
9. Summarize what was completed
10. State the next likely milestone

### Stream Title Guidance

Use a clear, searchable title that identifies both the series and the specific work.

Preferred format:

```text
Building KESMO #[episode number] | [Specific result or task]
```

The title should emphasize the result viewers will see rather than simply saying "coding" or "working on KESMO."

Use `Building CrownBound` as a separate series title when working on CrownBound.

### Stream Description Guidance

For every stream, place a brief stream-specific summary at the top.

Template:

```text
Today we are [specific goal].

Follow along as KESMO is designed, coded, tested, and published using HTML, CSS, JavaScript, GitHub Pages, Visual Studio Code, and AI-assisted development.

KESMO
Precision made simple.

Website:
https://kesmoworks.github.io/

GitHub:
https://github.com/KESMOWorks

YouTube:
https://www.youtube.com/@KESMOWorks

Relevant project:
[project name and live URL]

Relevant repository:
[repository URL]

#KESMO #WebDevelopment #JavaScript #GitHubPages
```

Change the first paragraph, project name, live URL, and repository URL for each stream.

Do not overload the description with excessive hashtags or repetitive keywords.

### KESMO Thumbnail Template Prompt

Use the established KESMO thumbnail as the design master and preserve its visual identity.

Do not redesign or reinterpret anything.

Keep exactly the same:

* Overall layout
* Blue gradient background
* Gold border
* KESMO logo
* Logo size and position
* Typography style
* Colors
* Lighting
* Shadows
* Spacing
* Line thickness
* Visual hierarchy

Only change the following text:

Main Title:

```text
Building KESMO
```

Episode Number:

```text
#[episode number]
```

Subtitle:

```text
[stream topic]
```

Do not add, remove, or move any other elements.

The finished image should look like the same branded KESMO thumbnail, with only the episode number and subtitle updated.

The stream topic should be more visually prominent than the episode number.

### Stream Safety

Before every stream:

* Enable Windows Do Not Disturb.
* Close email, banking, calendar, password manager, private messages, and unrelated tabs.
* Use a dedicated browser profile for streaming when practical.
* Hide bookmarks and personal browser information.
* Confirm no API keys, passwords, tokens, private repository information, analytics data, or personal details are visible.
* Check the OBS preview before going live.
* Prefer capturing specific application windows instead of the entire display when practical.
* Perform sensitive account or deployment work off-stream when necessary.

Do not expose:

* Passwords
* API keys
* Authentication tokens
* Private email
* Personal documents
* Payment or advertising account details
* Student or workplace information
* Private analytics
* Unreleased confidential plans

### Development and Streaming Principle

Decide privately when needed.

Build publicly when safe.

The stream should show implementation, testing, problem solving, and progress without unnecessarily exposing sensitive information or early business strategy.
